The 30-second version. A user dumped 76 messages = 59 photos + 5 distinct listings into a 1:1 chat. The pipeline split them correctly into 5 — then the dedup step merged 4 of the 5 back into 1 because a map pin belonging to one listing was applied to another, making distinct properties look co-located. One row survived; four were silently lost. This report shows exactly where, with the real data.

1 · How the pipeline works today

Ingestion is a cron-driven sweep that hands a conversation's whole un-ingested backlog to a six-step, per-segment LLM pipeline. Each step is a separate Anthropic call with a strict structured-output schema; each step has a deterministic fallback if the call fails.

Model assignment lives in packages/pipeline/src/steps/context.ts (STEP_MODELS). For a 59-image dump, classify is ~80–85% of all calls — and it is re-run from scratch on every retry, which is what made the dump time out three times before the mitigation.

How every step calls the API

One adapter (AnthropicStepLlm) makes every call the same way — messages.parse with a strict Zod output schema, the per-step system prompt carrying a prompt-cache breakpoint, and the user content (text, or an image block for classify):

await client.messages.parse({
  model,                 // per-step, from STEP_MODELS
  max_tokens,            // per-step cap
  system: [{ type: "text", text: SYSTEM_PROMPT,
             cache_control: { type: "ephemeral" } }],   // ← only the system prefix is cached
  messages: [{ role: "user", content }],                // text and/or { image } blocks
  output_config: { format: zodOutputFormat(schema) },   // ← strict structured output
});
// any error or schema mismatch → value:null → the step's own fallback runs

Because only the system prefix is marked cacheable, the per-image tokens in classify are paid in full on every attempt — they are not in the cached prefix. (adapters/anthropicStepLlm.ts, adapters/content.ts.)

2 · The prompts hitting the API

Each step sends a system prompt (verbatim below, verbatim from source) plus a user message built from the conversation. Several steps share four cacheable building blocks — shown once here, then referenced per step.

Shared building blocks (appended to the step prompts that use them)

These are concatenated onto the step prompts as noted. PREFIX_PAD is deliberate filler whose only job is to push the system prefix over the prompt-cache minimum (4096 tokens for Haiku/Opus, 2048 for Sonnet) so it stays cacheable.

DEED_TAXONOMY — used by classify, extract, gate

Thai title deed taxonomy (FIELD-02):
- chanote (โฉนดที่ดิน / น.ส.4จ): full ownership, GPS-surveyed, freely transferable.
- ns3g (น.ส.3ก): confirmed possession, aerial survey; transferable.
- ns3k (น.ส.3ข): confirmed possession, older survey; transferable.
- ns3 (น.ส.3): possession right; 30-day notice before transfer.
- spk (ส.ป.ก. 4-01): agricultural reform land — CANNOT be sold; inheritance only.
- pbt5 (ภ.บ.ท.5): tax receipt only, not a deed — cannot be sold.
- ns2 (น.ส.2): temporary occupation permit — cannot be sold.
- stg (ส.ท.ก.): forest-zone residence right — cannot be sold.
- sk1 (ส.ค.1): possession notification — cannot be sold; rare but circulates in chats.
- other: a stated document that fits none of the above.
- unknown: deed type not stated. NEVER guess a deed type that is not stated.

UNIT_GLOSSARY — used by classify, segment, extract, dedup, translate

Thai real-estate units and vocabulary:
- 1 ไร่ (rai) = 4 งาน (ngan) = 400 ตารางวา (square wah). 1 rai = 1600 m²; 1 ngan = 400 m²; 1 wah² = 4 m².
- ตร.ว. = ตารางวา (square wah). ตร.ม. = ตารางเมตร (m²).
- ล้าน = million THB; "4.5ล้าน" = 4,500,000 THB. ลบ. = ล้านบาท.
- นอน = bedrooms (3นอน = 3 bedrooms); น้ำ = bathrooms.
- ขายด่วน / ด่วน = urgent sale signal → urgency quick_sale.
- ขายฝาก = sale with right of redemption (khai fak) — a distinct transaction type.
- เช่า / ให้เช่า = rent; /เดือน = per month.
- ต. = ตำบล (tambon), อ. = อำเภอ (amphoe), จ. = จังหวัด (province).
- โอน = ownership transfer; มัดจำ = deposit/reservation; จะซื้อจะขาย = sale-purchase contract.

EXTRACTION_RULES — used by segment, extract

Extraction rules (apply to every field):
- Extract ONLY what the poster stated. Seller assertions map as-claimed (FIELD-11): never
  re-judge, verify, or substitute your own estimate for a stated direction, shape, price, or
  quota claim. Provenance is a UI concern, not yours.
- Absent string fields → "" (empty string). Absent numeric fields → null. Never invent values.
- Prices: normalize to THB integers (4.5ล้าน → 4500000). For rentals, priceThb is the MONTHLY rent.
- Phone numbers: keep digits and dashes as written.
- Set lowConfidence=true when figures conflict, the deed type is ambiguous between stated
  options, or you had to interpret heavily garbled text.

PREFIX_PAD — used by every step

Reference notes (stable, for terminology grounding): Thai property listings in LINE group
chats mix Thai and English freely, use regional abbreviations, and frequently omit fields.
[…the same sentence repeated 40× — pure cache-floor padding…]
STEP 1

classify + OCR

Haiku 4.5→ Sonnet on low-conf chanote

Runs once per photo on the 1568px derivative (never the original). Decides property / chanote / other; OCRs deed fields. Output feeds the [IMG n] kind — label markers in the transcript.

System prompt verbatim
You classify a single photo from a Thai real-estate LINE chat.
Decide if it shows a property (exterior/interior/land), a chanote/title-deed document, or other
(memes, stickers, screenshots, people). For title deeds, OCR the deed number, province, and the
area figures (rai/ngan/wah) if legible; set lowConfidence=true when the document is blurry or
partially visible. label is a 2-6 word content description.
+ DEED_TAXONOMY + UNIT_GLOSSARY + PREFIX_PAD

User content

[ image block: the 1568px JPEG, base64 ]
"Classify this image."

Output schema

{ kind: "property" | "chanote" | "other", label: string,
  deedNo: string, deedProvince: string,
  landRai: number|null, landNgan: number|null, landWah: number|null,
  ocrText: string, lowConfidence: boolean }
STEP 2

segment

Sonnet 4.6

Splits the thread into distinct property listings and attributes photos to each. This is the step that handles a multi-property dump — and in the incident it worked (5 segments).

System prompt verbatim
You split a Thai real-estate LINE chat transcript into distinct property listings
(segments) and attribute photos to them. A thread may contain one listing, several (a multi-property
dump), corrections, and re-posts. Photo markers appear inline in posting order; imageIndices refers
to those marker indices. If a segment plausibly matches one of the provided existing candidates,
set existingPropertyId; if it could match more than one, set ambiguous=true and list ambiguousWith.
A re-post of the same property within the thread belongs to the SAME segment, with the later
message treated as an update.
+ UNIT_GLOSSARY + EXTRACTION_RULES + PREFIX_PAD

User content

TRANSCRIPT:
<the whole timestamped transcript>

PHOTO MARKERS:
#0: property — house exterior
#1: chanote — title deed
…

GEO HINTS: 18.7298,98.9688; 18.8263,99.0564     ← the WHOLE conversation's pins

EXISTING CANDIDATES:
(none)

Output schema

{ segments: [ { label: string, imageIndices: number[],
                mapIndex: number|null,          ← which [MAP n] belongs to this segment
                existingPropertyId: string,     ("" = none)
                ambiguous: boolean, ambiguousWith: string[] } ] }
Bug seed. The schema computes mapIndex (which pin belongs to which listing) — but run.ts never reads it. So geo is handled at the conversation level, not per segment.
STEP 3

extract

Sonnet 4.6→ Opus 4.8 on lowConfidence

Pulls structured fields for one listing, focused on the named segment.

System prompt verbatim
You extract one structured property listing from a Thai real-estate LINE chat
transcript, focusing on the named segment. Later messages in the thread supersede earlier ones
(price corrections are common — use the corrected figure).
+ DEED_TAXONOMY + UNIT_GLOSSARY + EXTRACTION_RULES + PREFIX_PAD

User content

TRANSCRIPT:
<the whole timestamped transcript>

FOCUS SEGMENT: <the segment's label>

GEO HINTS: 18.7298,98.9688; 18.8263,99.0564     ← ⚠ ALL pins handed to EVERY segment

EXISTING CANDIDATES:
(none)

Output schema (24 fields; abbreviated)

{ dealType, propertyType, titleDeedType, priceThb: number|null, urgency,
  title, description, province, amphoe, tambon, landmark,
  lat: number|null, lon: number|null,            ← ⚠ the model may grab a foreign pin here
  landRai|landNgan|landWah|floorAreaSqm|bedrooms|bathrooms: number|null,
  facingDirection, contactPhone, posterName, lowConfidence: boolean }
The actual fault. Every segment's extract is handed the full geoHints array (run.ts passes geoHints: input.geoHints). A listing with no pin of its own can — and did — attach a coordinate belonging to a different listing.
STEP 4

dedup — block then verify

deterministic blockHaiku 4.5 verify

First a deterministic blocker finds ≤8 candidate matches (deed-exact → geohash cell + haversine radius → text similarity). Deed-exact auto-merges. Everything else goes to the Haiku verify call. Any failure defaults to "new."

System prompt verbatim
You judge whether a newly extracted Thai property listing is the same real-world
property as one of the provided candidates. Same property = same physical land/unit, even with
price drift, different phrasing, or different contact formatting. Different unit in the same
project = NOT the same. If uncertain, decide "new" — a false merge is the user-visible defect; a
missed merge is recoverable.
+ UNIT_GLOSSARY + PREFIX_PAD

User content

NEW LISTING:
title: …
type: sale commercial, deed unknown
price: 13800000 THB
where: ใกล้มหาวิทยาลัยแม่โจ้, …
size: 2800 m² land, ? m² floor
contact: ? (?)

CANDIDATES:
<id> (block score 0.85, geo_same_cell+geo_within_radius): commercial … 13800000THB
…

Output schema

{ decision: "new" | "merge", intoId: string ("" when new),
  confidence: number, reason: string }
Where the loss happens. When the geo mis-bind made two distinct listings share a coordinate, the blocker linked them on geo_within_radius and Haiku returned "merge" — folding a distinct listing into another instead of persistNewListing. The prompt already says "if uncertain, decide new," but a wrong-but-shared coordinate doesn't look uncertain to the model.

claims, no dropped caveats. Keep numbers, unit names (rai/ngan/wah stay as-is), proper nouns, and
project names unchanged. Tone: clear marketplace copy, not literary.
+ UNIT_GLOSSARY + PREFIX_PAD

User content

Translate from th to en.

TITLE: …
DESCRIPTION: …

STEP 6

gate

Sonnet 4.6+ deed blocks
System prompt verbatim
You are the listing quality gate for a Thai property marketplace. Given an
extracted listing, list the missing or weak fields a poster should be asked for, ordered by
importance. severity "required" = the listing cannot publish without it; "important" = should be
nudged for (CONV-01: photos are nudged, never hard-blocked). promptKey is a stable snake_case key
naming the field ask (e.g. "ask_price", "ask_deed_type", "ask_photos", "ask_location",
"ask_land_area", "ask_floor_area", "ask_utility_rate"). Do NOT decide deed-type legality — the
caller enforces deed blocks deterministically.
+ DEED_TAXONOMY + PREFIX_PAD

User content

LISTING (extracted):
{ …the extracted JSON… }
photoCount: 11

Output

{ pass: boolean,
  missing: [ { field, severity:"required"|"important", promptKey } ] }

Hard deed blocks (FIELD-03) and the "unknown deed never publishes" rule are enforced in code, under the model's list — the LLM only proposes the asks.

What each phase changes

PhaseGroupChangeWhy
1C — evalMake the incident a locked Tier-A regression case + add the "N distinct → N rows, 0 merges" metric the eval is currently blind to.Build the red test before the fix so the improvement is provable and can't regress.
2A — dedupBind geo per-segment (use mapIndex; pass only a segment's own pin) · conservative-merge guard (weak/uncertain merges become a new row + a moderation item, never silent loss) · honest count (report distinct rows persisted).Fixes the proven root cause and makes a false merge structurally impossible to lose data on.
3B — resilienceCache classify by s3Key (warm runs do zero classify calls) · chunk the batch, advance the watermark per chunk, then lower the 900s Lambda back to ~300s · smarter failure signal · write idempotency (E10) · a per-step timing hook.Kills the retry waste and the timeout cliff without the band-aid; makes re-runs safe.
4D — DMA DM dump becomes claimable by its sender (new dm_claimant_user_id + claim invite + gate admission).Today a DM listing is unclaimable by anyone — the "seed my account" user can't use their own data.

Ordering rationale (full detail in 00-CONSOLIDATED-sequencing.md): silent data loss is the worst defect, so A precedes B — shipping chunking first would spread the merge bug across chunk boundaries, whereas A's conservative-merge makes any cross-chunk split a recoverable duplicate.
